# 震源推算整改代码与性能核验（2026-10-14）

核验对象为《震级算法与预估震度整改总结_20261014.md》及本机实际源码。本文审阅生产实现、实测开销，不重新标定公式或修改生产发布策略。核验源码快照、差异和日志保存在 `D:/flutterApp/flutter-source-estimation-audit/20261014-162309/`，对应文件 SHA-256 见 `metadata.json`。仅隔离验证工程添加计时，生产算法及 UI 未修改。

## 实现核对

1. 震级公式已实际使用 `0.7016 * processedIntensity + 0.0903 + 1.73 * log10(distance)`，保留负数结果钳到 0、20 km 距离下限、既有量化及 scratch 最近站查询。唯一生产调用点已传入 `request.observedAt`。
2. 发布状态允许同报输入震度改善后再次发布；震源稳定且最后改善超过 10 秒才锁定。这里的 10 秒是项目实现参数。不能仅因代码注释引用 JMA 就把这个具体参数称为官方参数。
3. UI 已使用静态的 4360 站表计算最大预测震度，深度大于 150 km 或 M/深度缺失时返回无震度；徽章文字、色类随预测结果。测站 Map 表是一次性静态构造，**没有每次重建 4360 个 Map**。预测结果本身没有缓存。
4. 源估仍是 widget 内的显示投影。provider/TTS 没有摄入 `nied_source_estimation` 或 `palert_source_estimation` 的生产路径；语音辅助仍为普通 EEW/信息前缀，未发现文档说已撤回的源估语音分支残留。Rust 源码没有 magnitude/震级实现，当前震级计算确在 Dart。
5. 本次重跑震级、震源估计、源估卡片、NIED 驱动共 **62 项测试通过**。这验证当前实现与现有断言，不等于独立复验 K-NET 标定、科学模型或文档全部语料统计。

## 文档需要补充的边界

### 发布锁锁定后的新报次

`SrevKaizouMagnitudePublicationState.update()` 的 `if (_locked) return _publishedResult` 在报数变化的重置判断之前。因此“报变更即按新震源重导”只适用于尚未锁定的状态；锁定后即使换报数，也不会进入 calculate。源合并时 `copyFrom` 还会保留此状态。这个事实与总结没有限定范围的说法存在差异。是否需要最终锁之后按新震源解锁属于发布规则决策，本文没有擅自改动，也没有把静态边界当作已经复现的现场故障。

### P-Alert 的影响范围

`_sourceUnifiedEvents` 把 NIED 和 P-Alert 都交给同一个 V2 显示函数。`PAlertSourceEstimation` 当前两处构造 `SourceEstimate` 都不设置 `magnitude`，所以新预测函数会返回 null，徽章变成无震度。即使以后接入 M，这个函数仍使用日本 JMA 4360 站集合，而不是台湾测站集合。总结写的是源估统一显示，未明确列出这一影响。本文没有改回检出震度或填造震级。

### 计算频率

文档“输入震度每上升一次就重算并发布”的说法只准确描述发布条件。实际 `update()` 在未锁定期间每次先执行 `calculate()`，再比较 inputIntensity；完整计算会扫描 1748 个 scratch 站找最近站。未改善的输入仍付出这部分开销。UI 预测则在 `_sourceUnifiedEvents` 执行时求值：源事件变化、相关 provider 显示状态更新和翻页都可能触发，**不应将它直接等同于每个渲染帧都计算**。

## 组件实测

用现有原始 NIED 回放实际产生的 49 个 source estimate 的经纬度、深度、震级作为性能输入，不把参考地震目录标签加入推算。Dart 3.11 AOT 可执行文件调用原生产 `calcMaxJmaShindo`、原 4360 站和 ARV：预热 100 次，5 轮各 300 次。

| 指标 | 结果 |
| --- | ---: |
| 每轮平均 | 0.760–0.775 ms |
| 每轮中位数 | 0.744–0.746 ms |
| 每轮 P99 | 1.051–1.164 ms |
| 首次预测调用 | 0.844 ms |
| 一次性构造站表 | 0.721 ms |

文档“量级小于 1 ms”对本机平均/中位数基本成立，不是每次都低于 1 ms，更不适用于未经测量的设备。该组件程序 RSS 从约 14 MiB 到 49 MiB 包含 Dart 运行时、堆容量及反复计算的临时分配，不能解释为 4360 站表永久占用 35 MiB。详见 `component.json`。

## 完整 APP 对照方法

两个隔离 Windows Profile/AOT 构建使用同一工作树、同一设置与原始输入，仅三个文件切换整改前/后：`srev_kaizou_magnitude.dart`、`source_estimator.dart`、`alert_module.dart`。前版取自此前保存的修改前 ZIP；差异核对后，source_estimator 仅多一行 observedAt，另外两份正是文档列出的三项变更。保留此前已完成的原生推算、地图和归档优化，不拿旧的未迁移版本当基线。

输入是保存的 288 个原始 NIED GIF 及同时到达的 4 报原始 JMA EEW；外部网络源在隔离工程停用，历史时钟按原观测时间推进，原报文不改写。预测/震级计时只写独立诊断文件，不进入推算输入或原报文。CPU 取进程占全机逻辑核百分比，GPU 取该进程各 PDH 引擎的最大占用。运行期间没有同时编译或测试。

预先固定两个统计窗口：第 30–320 秒（整体活动），第 80–150 秒（该原始样本震源推算活跃段）。同时查看完成画面帧数、帧耗时及预测调用频率，不能用减少完成帧数换来的占用下降称为同等体验的收益。整机记录是受控 Profile 验证，不是当前安装版 Release 的任务管理器读数；本次功能会有意改变震级及预测徽章，所以不要求新旧所有数值完全一致。

第一次当前版回放 `current-run` 在第 91 秒进程退出，未写完成标记，不纳入完整性能比较。用户回复可能误点击了测试窗口关闭按钮；系统没有检索到对应 Application Error/WER 记录，不能据此判定算法或原生崩溃。使用同一二进制、重新复制的相同设置及独立目录复跑，最终比较目录为 `before-run` 和 `current-repeat-run`。复跑额外监控退出码，未覆盖中断记录。

完整 APP 中的预测计时包含首次静态站表求值以及同步计算期间的线程调度影响，不能和预热后的独立组件均值混为一谈；生产函数没有缓存，这 52 次中 46 次（88.5%）输入参数与此前相同。增加的震级计算本身累计不足 1 ms，不能根据调用次数增加五倍就说 CPU 增加五倍。当前证据不支持把此前的大幅 CPU/内存占用主要归因于这三项整改。

两版均完成 288 个 GIF、4 报 EEW、49 次有效 source estimate。新旧源位置、深度、置信度、发震时间及站数逐项一致；震级按预期从旧版固定 `1.8107818924986874`，变为 `2.6918818924986874 → 3.1549378924986873 → 3.3934818924986874`。四报 EEW 完整对象相同，2,535 个原文件 SHA-256 全部未变。没有 Flutter 框架/布局错误捕获文件；stderr 仍有隔离环境主动拒绝外网产生的 `Diagnostic offline fixture` 异常，不能声称全部日志零异常。

验证工程的预测/震级计时、每秒诊断落盘及 VM heap 采样也有开销，因此上述数据只用于这对隔离构建的相对比较，不能直接视为用户安装版的实时值。细节在 `comparison.json`、各运行目录及 `current-repeat-run/exit-status.json`。生产三个文件的定点静态分析为 **No issues found**。

## 优先级建议

1. 先对源估预估震度按完整的 M、深度、经纬度及预测区域/模型做有界缓存，输入不变时复用已算结果；不能降精度或减少测站来代替。它针对已实测的 88.5% 重复请求，有助于减少 UI 同步工作，但不能承诺整机 CPU 同比例下降。
2. 最近 scratch 站查询可以按原有四舍五入后的源坐标复用，再在输入峰值改善时计算标量公式。但本次累计不到 1 ms，优先级低，不值得仅为了这条小公式增加一次 Rust/FFI 迁移。
3. 明确最终锁是否允许后续新报/震源要素修订重导，以及 P-Alert 预估震度的区域与震级来源，再调整相关业务规则。本文只报告现状，没有改动作者的新系数、10 秒阈值、缺参显示或源估语音边界。
