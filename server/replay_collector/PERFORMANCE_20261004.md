# 录制与导出性能实测

日期：2026-10-04。服务器：原有四核、约 4 GiB 内存实例。

结论：短回放的保存完整性通过，但保存性能不通过；五分钟双回放导出未完成。
空闲接收的图片解码修复，不代表活动录制与导出的内存问题已经解决。

## 测试边界

- 使用独立 native Release 探针、Xvfb、独立 systemd cgroup 和独立数据目录。
- 复用正式采集的七个测站适配器；不启动 Jian、GQ、ICL、SeedLink 或 TG 上传。
- CWA、CEA 使用仓库原始回放报文，报文内容、震源时间、测站读数及源 JSON 未改写。
- 历史报文通过独立检查点建立测试窗口；仅测试接收时钟由 Stopwatch 驱动。
  这些文件是性能测试产物，不是对应历史地震的真实测站观测回放。
- CPU 配额为一个核心，MemoryHigh 为 640 MiB，MemoryMax 为 896 MiB。
- 100 ms 采样 RSS、cgroup 内存和 CPU/I/O 计数。CPU 表示测试进程组对四核整机的贡献，
  不包含同时运行的正式采集、KMA、网盘等服务。RSS 和 cgroup 内存不是同一口径。
- 审计复制和导出后校验单独分阶段，不计入录制阶段 CPU。文件大小为逻辑字节数。
  cgroup I/O 的异步回写可能跨阶段，不将导出阶段写入计数等同于回放文件大小。

## 实测结果

| 场景 | 录制 RSS 峰值 | 录制平均 CPU（折算四核） | 导出 RSS 峰值 | 结果 |
| --- | ---: | ---: | ---: | --- |
| 一分钟单回放 | 331.3 MiB | 14.40% | 633.8 MiB | 21.592 秒导出，完整性校验通过 |
| 五分钟双回放 | 640.3 MiB | 21.53% | 784.4 MiB | 导出观察约 334 秒未完成，主动停止测试 |

- 单回放实际接收时段：北京时间 23:30:41 至 23:31:40。760 帧，包含 KMA 60、
  TREM/CWA 56、SeisJS 474、S-net 2、NIED 51、P-Alert 58、LPGM 59。
- 单回放检查点共 12 个，35442806 字节；最终 rqreplay 为 31489396 字节。
  原始报文集合一致，每一帧与检查点的完整 JSON SHA-256 对应一致，无遗漏或额外帧。
- 单回放文件 SHA-256：
  `a87c36b4802fd1250020fb7ad7daf1457fea78b8110b7b3f107a183f6fb2c4a0`。
- 双回放实际接收时段：北京时间 23:14:45 至 23:19:45。每条测试窗口接收 3436 帧；
  两条合计 53 个检查点文件、309115071 字节（约 294.8 MiB）。
- 双回放 26 次检查点，20 次超过 5 秒，最长 22.601 秒，出现录制积压。
- 双回放导出中读取并展开历史分块，内存持续增加；DartWorker 实际阻塞于
  `mem_cgroup_handle_over_high`。停止前 memory.events 的 high 为 42197，oom/oom_kill 为 0。
  这是软限流导致的导出停滞，不是已经发生硬限制 OOM。
- 双回放没有 exported、verified、done 标记，也没有最终 rqreplay。主动停止后的
  systemd Result=success 仅表示服务停止成功，不能当作测试通过。
- 失败的原始检查点和审计副本保留，正式采集目录、上传队列未修改。

## 定位

`ReplayCollector._checkpoint` 对不同活动事件分别复制 pending 并重新编码。
`_exportCapture` 持续把所有分块解码后的测站帧积累在一个 List，之后再整体生成 JSON。
实测确认这两个阶段的开销不能用空闲接收的约 250 MiB RSS 估计。

原始采样报告位于本地 `build/performance/20261004-recording-probe/`：
`single-60s-report.json`、`dual-300s-report.json`。双回放报告为初版监测器产物，
判定失败须查看无导出/校验/完成标记，而不是只看 systemd 状态；后续监测器已增加 passed 判定。

这次只补测并保留证据，未把新的存储/导出优化部署到正式服务。正常采集继续运行，
已有资源限制保持生效；不能承诺活动保存时 CPU 保持个位或内存保持 200 MiB。
